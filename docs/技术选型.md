# 技术选型

状态：已确认（2026-11-07）

## 需求边界

- 导入题目文档（.docx），自动识别并拆分题目。
- 题目自动排版，支持手动调整题目间距等版式参数。
- **只导出 Word（.docx）**，同一工程可导出教师版（教案）与学生版（学案）。PDF 由老师在 Word / WPS 中自行另存，软件不实现。
- 每份教学案保存为一个独立的工程文件，便于本地管理。
- 字体使用系统自带的常用字体，外观与参考样例接近即可，不追求像素级一致。
- 平台：**先做 Windows**，功能较完整后移植 macOS。从第一天起按跨平台方式编写代码。

## 选型总表

| 层面 | 选择 | 说明 |
|---|---|---|
| 桌面框架 | Electron | Windows 与 macOS 使用同一个 Chromium 内核，预览效果一致 |
| 语言 | TypeScript（主进程与界面统一） | 全项目单一语言 |
| 界面 | React + Vite | 生态成熟，组件丰富 |
| 富文本编辑 | TipTap（基于 ProseMirror） | 编辑题干、选项、详解 |
| 公式编辑 | MathLive | 可视化输入，产出 LaTeX |
| 公式显示 | MathML（Chromium 原生渲染） | OMML → MathML 后直接显示 |
| 拖拽排序 | dnd-kit | 调整题目顺序 |
| docx 读写 | JSZip + 直接操作 OOXML | 导入解析与模板化导出共用一套 XML 工具 |
| 工程文件 | 自定义扩展名的 ZIP 容器 | 见下文 |
| 打包 | electron-builder | Windows 出 NSIS 安装包，日后同一配置出 macOS dmg |
| 测试 | Vitest | 识别与导出逻辑以样例文档做回归测试 |

## 关键决策

### 1. 为什么从 Tauri 改为 Electron

原方案选择 Tauri，主要是为了内嵌 Rust 编写的 Typst 来生成 PDF。取消 PDF 后，这一优势消失，而 Tauri 的劣势依然存在：Windows 上使用 WebView2（Chromium），macOS 上使用 WKWebView（Safari 内核），两端的 MathML 渲染和排版细节存在差异，移植 macOS 时需要额外适配。Electron 在两个平台上内核完全相同，且整个项目只需 TypeScript。安装包较大（约 100 MB），对内部分发可以接受。

### 2. Word 导出：模板注入

以参考样例中的 `styles.xml`、`numbering.xml`、页眉页脚为模板，软件只生成 `document.xml` 的正文。这样导出的文档会沿用 `物理排版 *` 样式，`【答案】【知识点】【重点】【难点】` 继续由编号自动生成，老师二次编辑时体验与现在一致。

字体：中文宋体、西文 Times New Roman、公式 Cambria Math。Mac 版 Word 会自动替换为对应字体，无需特殊处理。

### 3. 分页交给 Word

由于最终分页由 Word 决定，软件内预览只做近似分页。排版参数尽量映射为 Word 原生属性，使效果在 Word 中依然成立：

| 软件中的排版参数 | Word 中的实现 |
|---|---|
| 题后留白（学生作答空间） | 段后间距或空段落 |
| 题目不跨页 | `keepNext` / `keepLines` |
| 从新页开始 | `pageBreakBefore` |
| 选项列数（1 / 2 / 4 列） | 制表位对齐 |
| 题图位置（下方 / 右侧） | 嵌入式图片 / 四周环绕浮动图片 |

### 4. 公式：保留原始 OMML

每个公式同时保存原始 OMML 与 LaTeX：

- 未修改的公式：导出时原样写回 OMML，零损失。
- 新建或修改的公式：MathLive 产出 LaTeX → MathML → OMML。
- 显示：OMML → MathML，由 Chromium 渲染。

### 5. 工程文件格式

单个 ZIP 文件（扩展名待定），结构如下：

```
manifest.json      格式版本号、创建软件版本、时间戳
project.json       元信息、章节与题目块、排版参数
assets/            图片等资源，以内容哈希命名，自动去重
```

保存时先写临时文件，再替换原文件，避免断电导致工程损坏。格式版本号用于后续升级时自动迁移旧工程。

## 跨平台约定（从第一天起遵守）

- 路径一律用 `path` 模块拼接，支持中文与空格路径。
- 快捷键用 `CmdOrCtrl` 写法。
- 不依赖仅 Windows 存在的组件（如 COM 调用 Word）。
- EMF / WMF 图片在导入时转换为 PNG，转换器需选用跨平台方案（待调研）。
- macOS 的签名与公证留到移植阶段处理。

## 待调研风险

1. OMML ↔ MathML ↔ LaTeX 转换库的覆盖度，需用样例中的 332 个公式逐一测试。
2. 题库文档中的 MathType OLE 公式对象如何处理（转图片或转 OMML）。
3. EMF / WMF 的跨平台转换方案。
